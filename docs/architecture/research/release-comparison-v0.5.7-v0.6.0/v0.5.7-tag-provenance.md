# The v0.5.7 tag does not match the published v0.5.7 JAR

Recorded 2026-10-12. Nothing was changed: the tag, the release and its assets are as they were found.

## What was found

The git tag `v0.5.7` points at `7b5b3a4332193d28a1f668654806fac434f2cb8f`, the merge of PR #179 into master on 2026-04-19. Its POM version is `0.5.7-SNAPSHOT`.

The published `engine-uci-0.5.7.jar` was built from a different commit, `beaef361d35160d768473af7d2c349719db8508b` ("chore(release): v0.5.7", 2026-07-07 14:03:58 UTC). The GitHub release was published at 14:04:08 UTC the same day, ten seconds later. It was created as a release on 2026-04-19 (targeting `master`) and published in July, which suggests the tag was set in April and not moved when the release was cut in July from the develop lineage. No record of why was found.

`beaef36` is not reachable from the tag commit. 37 commits reachable from `beaef36` are missing from the tagged commit, among them the merge of the Phase 14 eval-optimization work (PR #184). `beaef36` is an ancestor of `v0.6.0`. The tag commit was the head of master until PR #251 merged develop into it for v0.6.0.

## Evidence

Each commit was built in a detached worktree (`mvn -pl engine-core,engine-uci -am package -DskipTests`, OpenJDK 21.0.12.1, Maven 3.8.7). JARs are not byte-reproducible, so whole-file hashes cannot be compared. The SHA-256 of every `.class` file inside each shaded JAR can be, and the listings are archived in [`identity/`](identity/).

| JAR | Classes | Listing digest (first 16 hex) |
|---|---:|---|
| published `engine-uci-0.5.7.jar` (SHA-256 `bc41c91b0d3b4c20f6a334ff3f0cc2cf5c04e6820b817b1cfd46e62a640663d3`) | 736 | `77cd88805a63d380` |
| rebuild of `beaef36` | 736 | `77cd88805a63d380` (identical, class by class) |
| rebuild of the tag commit `7b5b3a4` | 736 | `8af6956e7a689e54` |

The tag rebuild differs from the published JAR in 13 classes: `EvalParams`, `Evaluator`, `KingSafety`, `PawnStructure`, `Board` (and its four inner classes), `MovesGenerator`, `Searcher`, `BenchRunner` and `UciApplication`.

The difference is visible in behavior. At depth 13 on 29 benchmark positions, the published JAR searches 54,546,076 main nodes and the tag build 58,104,689. The published JAR's own `BenchRunner` has 31 positions; the tag commit's has 33.

The same check for v0.6.0 is clean: the published `engine-uci-0.6.0.jar` and a rebuild of `bc3dc380e759526e8aa19cd8385af16ab22ac502` have identical listings (791 classes), and the tag `v0.6.0` points at that commit.

To verify without rebuilding: unzip a JAR into an empty directory and run
`find . -name '*.class' | LC_ALL=C sort | xargs sha256sum | diff - identity/classes-published-v0.5.7.sha256`.

## Consequences

- Building "v0.5.7" from the tag gives different code from what users downloaded. Any comparison, bisect or benchmark that checks out the tag measures the wrong source.
- The release comparison in this directory uses the published JAR and `beaef36`. `tools/release-comparison.ps1` refuses to run if its v0.5.7 arm resolves to the stale tag commit.
- The `v0.5.7` tag is covered by the `immutable-release-tags` ruleset, so it cannot be moved or deleted without an audited ruleset change. This note does not recommend one. Pointing readers at `beaef36` is enough, for example in the release notes or the changelog entry for 0.5.7. That edit, and any change to the release, is left for the maintainer to decide.
