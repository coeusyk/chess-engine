# QA 1016 / QB 128 end-to-end compatibility (#265)

2026-11-25. The weight-scale note (`docs/architecture/research/nnue/2026-11-24-weight-scale-alternatives.md`) measured that a larger first-layer grid cuts quantization error several times, and left one open point: nobody had checked that the rest of the stack copes with QA above 127. This note answers that for QA 1016 / QB 128, from the trainer's serializer to the Java vector paths. It changes no quantizer, default scale or network, and retrains nothing. #265 stays open.

Two kinds of evidence are used and they are kept apart throughout. A **real-checkpoint measurement** is a number taken on a network that was actually trained. **Synthetic compatibility evidence** comes from a seeded random network that exists only to exercise arithmetic, so it says the machinery works at this scale and says nothing about how a trained network will play.

## What each layer does at QA 1016 / QB 128

| Layer | Result |
|---|---|
| Trainer `quantize()` | Does not depend on QA. It rounds to nearest, clips to int16 and checks the worst-case 32-feature accumulator. `validate_qa` allows 1 to 32767 and `validate_qb` any integer of 1 or more. |
| Exporter and header | `qa`, `qb` and `outputScale` are int32 header fields, so the file says which grid it uses. `qa` is checked against int16. |
| Trainer clip bounds | `derive_weight_clip_bounds(1016)` gives a bias clip of 1016 and a weight clip of 992. The checkpoint below peaks at 156. A network trained at QA 1016 chooses its own scale, which is a training question this note does not cover. |
| Java loader | Accepts `qa` 1 to 32767 and any positive `qb`, and rejects a network whose worst-case accumulator can leave int16. |
| Accumulator and incremental updates | Plain int16 add and subtract with no QA in the arithmetic. |
| Scalar inference | `long` products and a `long` division, so the output sum cannot overflow however large the weights are. |
| Vector accumulator ops | Elementwise `short` add and subtract, again no QA in the arithmetic. |
| Vector output dot (#313, not merged) | Uses int lanes only when `qa * sum(abs(w))` fits an int, otherwise the scalar loop. Its own tests cover the guard boundary. |
| Hard-coded 127 in production code | None found. The only QA constant in main code is the loader's upper limit, 32767. |

Nothing in production code needs to change for a network at this scale.

## Real-checkpoint measurement (one checkpoint)

**Checkpoint.** P5 control final, `trainer/outputs/phase5/P5-AUXHEAD-RMS/control/final.pt`. The file is gitignored and is not in the repository. 2,382,303 bytes, SHA-256 `fef3ee900c5973016ca589fac2146f28eed48e7b9812eb6d78bbd2d9380b11bb`. Config: hidden width 256, qa 127, qb 64, output scale 400, seed 42, 20,000 steps. This is the checkpoint the #312 note calls P5 control final.

**Corpus.** The 393 positions of `bench/nnue-corpus` (`tactical`, `quiet`, `opening`, `middlegame`, `endgame`, `random-legal`), `fen_corpus_sha256` `08ea323986d6bebbb5106f56c135afe836a182b3343424053712d4cdd70aeb39`. This is not the checkpoint's own held-out set.

**Method.** The checkpoint was rescaled so the float function is unchanged (`scripts/analyze_scale_alternatives.rescale`, first layer and QA by 8, output layer and QB by 2, output bias by both), once at factors 1 and 1 (QA 127 / QB 64) and once at 8 and 2 (QA 1016 / QB 128). Each was quantized with the production `quantize()` and serialized with the exporter's byte writer. The Python quantized reference scored the corpus. The real Java loader and evaluator then read the same files and were compared with those scores, and the incremental accumulator was checked over random games.

**Commands.** The Python half ran on develop at `be7cfff`, the Java half on `origin/phase/32-nnue-vector-dot` at `1de80b2` (develop plus #313, so the vector dot kernel was in the run). Both scripts are in `2026-11-25-265-qa1016-qb128-probe/`.

```
# Python half, from trainer/ of a develop checkout
PYTHONPATH=. python ../docs/engineering/investigations/2026-11-25-265-qa1016-qb128-probe/probe265.py <checkpoint> <out_dir>

# Java half, from the repository root of a #313 checkout, after copying ScaleProbeTest.java.txt to
# engine-core/src/test/java/coeusyk/game/chess/core/eval/nnue/ScaleProbeTest.java (do not commit it)
mvn -q -pl engine-core test -Dtest=ScaleProbeTest -Dprobe.dir=<out_dir> \
    -DargLine="--add-modules jdk.incubator.vector -Dprobe.dir=<out_dir>"
```

**Results.** Full output and hashes are in `results.txt`. Per scale:

| | QA 127 / QB 64 | QA 1016 / QB 128 |
|---|---|---|
| FT max abs weight, int | 19 | 156 |
| Loader bound violations | 0 | 0 |
| Java equals Python reference | 393 of 393 | 393 of 393 |
| Incremental vs scalar rebuild, 2,400 random-game checks | 0 diverged | 0 diverged |
| Incremental `evaluate()` vs rebuild `evaluate()` | 0 diverged | 0 diverged |
| `qa * sum(abs(output w))` over the int32 limit | 0.0007 | 0.0106 |
| Vector dot kernel (#313) vs scalar | 393 of 393 | 393 of 393 |
| Accumulator range, corpus | [-82, 50] | [-649, 391] |

The comparison is within each scale, Java against Python on the same bytes. No score is compared across scales: a different grid rounds differently, which is the quantization error the #312 note measured. The score files reproduce bit for bit on a second run. The exported `.nnue` bytes do not, because the header carries the export time; both sets of hashes are in `results.txt`.

On this corpus no accumulator reached `qa` at either scale (`valuesAboveQa=0`), so this checkpoint never exercised the upper clamp. That coverage comes from the synthetic fixture below.

## Synthetic compatibility evidence (committed)

A frozen QA 1016 / QB 128 fixture sits next to the two QA 127 ones, produced once by the real exporter and never regenerated. It is a seeded random network: width 64, weights drawn with `numpy.random.default_rng(1016)` (feature weights N(0, 128), biases N(240, 200), output weights N(0, 80)), output bias -123, output scale 400. The generator is `gen_fixture.py` in the probe folder and the exact snippet is in `engine-core/src/test/resources/nnue/README.md`.

- `parity-w64-qa1016-fixture.nnue`: uuid `bccce5bc-0538-4c33-8350-0f15e5270496`, trainer commit `eeeeeeee`, created `1795583643`, 98,784 bytes, SHA-256 `af9571a08981fb48132ae26cbeee7b1d21adb2a4a107fcda728160585953093d`.
- It was chosen so the corpus reaches both clamps and negative truncation: accumulator values above `qa` are 4,490 of 50,304 (8.93 percent), below zero 17,753 (35.29 percent), and scores run from -2152 to +2618 with 178 of 393 negative. The tests assert these, they do not assume them.
- `bench/nnue-corpus/fixture-w64-qa1016-golden-evals.csv` holds the Java int16 score for every corpus FEN. The trainer test checks Python against it with zero difference, and the Java test checks the live evaluator against it. The two existing CSVs are unchanged.

Other tests added:

- The incremental-versus-rebuild fuzz now also runs at width 256, QA 1016 / QB 128, on a synthetic network at about eight times the QA 127 weight scale, covering every move type and null moves.
- `NnueNetworkLoaderTest.scalarEvaluationIsExactWhenTheOutputSumExceedsInt32` uses an output layer of all 32767 weights, asserts `qa * sum(abs(w))` is over `Integer.MAX_VALUE`, asserts that real positions produce a raw sum outside int32, and checks `evaluate()` against an independent `long` reference. This is scalar coverage on develop, where there is no guard or vector dot.
- `NnueNetworkLoaderTest.evaluateAtTheLoaderBoundEdgeDoesNotWrap` loads a network whose accumulator sits at 32,760, just inside int16, and checks it neither wraps nor moves.

## What this does not establish

- **Guard rejection and vector fallback.** `dotFitsInt` and the vector dot kernel exist only on #313. The overflow fixture above is therefore scalar coverage. A test that the guard rejects it and that the vector path falls back to an equal result is Task 5 of the plan and waits for #313 to merge.
- Other checkpoints. One real checkpoint was run end to end. The #312 note's static headroom figures cover the other twelve, which is weaker evidence.
- Play strength. Everything here is arithmetic agreement and headroom.
- Training at QA 1016. Initialization, learning rate and clipping all depend on QA, and a network trained at this scale would choose its own. That is a retraining question and was not touched.
