# Screening readiness: how checkpoints are identified, selected and checked

2026-11-27. Plan #329 (slice 3), referring to #265 and the staged protocol in the strength assessment (#327). This note records what exists to make the existing checkpoints ready for staged screening, how the shortlist is decided, which checks are hard gates and which are only measurements, and how to run all of it. **Nothing has been run on the real checkpoints yet.** The real inventory, the exports and the Stage 0 runs wait until the host is free, and no result below is a measurement of a real network.

## Identifying a network

`export()` assigns a fresh uuid and the current time on every call, so two exports of one checkpoint have different file hashes, and two checkpoints with the same tensors but different training metadata have different checkpoint hashes. The 2026-11-24 audit shows the consequence: `P1-G04` and `M-1 cp-only seed 42` have identical figures and the project already treats them as one network, yet their file hashes differ. File hashes cannot find duplicates.

`trainer/export/identity.py` adds two content hashes. `tensor_sha256` covers the float network and `network_content_sha256` covers the int16 network the engine would load. Both cover every inference-relevant parameter, not only the arrays: `hidden_width`, `qa`, `qb`, `output_scale`, the architecture id, the feature-set id, `output_bias`, the quantization version, and each array with its name, dtype and shape. They exclude the uuid, trainer commit, timestamps, dataset composition and all checkpoint metadata. Two networks that differ only in `qa` or `output_scale` hash differently even with equal arrays.

## The shortlist

`trainer/export/shortlist.py` with the committed `shortlist_groups.json` is a pure function of the inventory (labels, `network_content_sha256`, and the checkpoint hash when present). It reads no measured quality, so it can be fixed before anything is rescored.

**Policy: deduplicate network execution, not experimental relationships.** The unit is the group (the anchor, a baseline, or a paired comparison), kept whole or dropped whole so a control and its treatment are never split across the cap. A network is its `network_content_sha256`. A comparison with an arm identical to an already selected network reuses that network and adds only its distinct counterpart, a comparison whose arms are all selected costs nothing and is kept, and a comparison whose two arms are identical to each other is kept and flagged `identical_arms`. Each selected group lists what it deployed (`new_networks`) and what it reused and from which group (`reused`), so the arm relationship survives. The budget is 10 distinct candidate networks plus the E-3 anchor, so at most 11 distinct networks (the #327 stage 1 budget reads "about 10 nets and the E-3 anchor"; the first version counted the anchor inside the 10, which was the wrong reading and is corrected here, frozen before any real checkpoint was measured). The anchor group is outside `candidate_cap`, the candidate count is distinct deployed identities once each, and a candidate arm identical to the anchor's network reuses it at no cost. A group that would take the candidate count over the cap is skipped whole and the next one considered, so the tie-break at the cap is the fixed order and nothing else. A group that adds no new network always fits. Checkpoint-level provenance is kept: the output also lists every deployed network with every inventory label that has its identity and their checkpoint hashes, including checkpoints that are in no group (this is where `M-1 seed 42` appears next to `P1-G04`).

This replaces the first version, which dropped a whole comparison when either arm duplicated an earlier network. That would have removed the E-16 seed 42 pair if its control turned out identical to the baseline, which discards a relationship in order to save a network that costs nothing to reuse.

**Priority, and why it changed.** The first committed order was chronological: the anchor, P1-G04, P3A-001, P4IV, then the P5, E-15 and E-16 pairs, then the M-1 seeds. #327 states no shortlist order, only the budget and the screen's purpose (drop nets scoring below 0.10 in 60 games), and the first order does not follow from that. A 60 game screen that only drops hopeless nets learns most from one representative of each distinct training signal, because nets that share a recipe are expected to land in the same place. The order is now written down in the file with a reason for each group:

- **Tier A, the reference and the base recipe:** E-3 (the only net that has played) and P1-G04. M-1 seed 42 is the same network and is recorded as a label of it.
- **Tier B, one representative of each distinct training signal:** P4IV (outcome blended into the target), the P5 pair at its selected step (auxiliary WDL head, because that run recorded a selection rule), the E-16 seed 42 pair (Stage 3 self-play with a shared opening prefix, the cleaner design) and the E-15 pair (the earlier self-play design, whose control collapsed).
- **Tier C, replicates of a represented recipe, which give the spread needed to read any difference between recipes:** M-1 seeds 43 and 44 (pure seed replicates) and P3A-001. P3A-001 differs from the base recipe by 75 sentinel rows and its held-out figure (+0.0002 over P1-G04) is inside the M-1 seed spread (0.5898 to 0.5977), so on the one metric available it is no more informative than a seed replicate. It no longer precedes the M-1 seeds. E-15 stays in tier B, ahead of the seed replicates, because it is a different data source, not because its design was good.
- **Tier D, later checkpoints and further seeds of represented recipes:** the P5 pair at the final step and the E-16 seeds 43 and 44.

With all identities distinct the first eight groups take the anchor and exactly 10 candidates (P1-G04, P4IV, the P5 selected pair, the E-16 seed 42 pair, the E-15 pair, M-1 seed 43 and M-1 seed 44, so 11 networks in all), and P3A-001 and tier D are cut by the cap with the reason listed. If a shared arm or a duplicate is found on the real checkpoints, the freed slots go to the next groups in order. The order is a judgment and not a measurement. Moving a group is a one-line change to the file, and nothing is selected before the inventory has run.

## Hard gates and measurements

An export (`scripts/export_screening_net.py`) writes the `.nnue` and manifest with the public exporter, unchanged, and a sidecar `<uuid>.screening.json` next to them (no change to the exporter or the manifest schema). `scripts/screen_stage0.py` adds the checks that need the network file. Each gate is pass or fail, and `not run` is never a pass. The sidecar is written last, so a process killed between the export and that write leaves a `.nnue` and `.json` with no sidecar. The duplicate scan does not see such a pair, and it should be deleted and exported again. Only sidecars that say `exported` count for duplicate refusal, so a failed gate does not block exporting the network again.

| Check | Kind | What it is |
|---|---|---|
| Identity | hard gate | The network read back from the file equals the quantized network array for array and scalar for scalar, the header uuid equals the manifest uuid, and the file SHA-256 equals the manifest's `nnue_sha256` |
| Loader safety | hard gate | `assert_java_loadable` (the worst-case accumulator bound the Java loader enforces), and with an engine JAR the real strict engine loads the file through the pre-flight with the pinned uuid and hash |
| Java against Python parity | hard gate | The real engine's integer score (`position fen` and the UCI `eval` command, the `int16 score` line) equals the Python reference on the committed 393-position corpus and the controlled positions, difference exactly 0. #265 established bit-exactness on committed fixtures, so there is no tolerance |
| Controlled orientation | hard gate | The correct sign on every one of 24 controlled positions |
| Duplicate refusal | hard gate | An export whose `network_content_sha256` is already in the output directory is refused unless `--allow-duplicate REASON` is given, and the reason is recorded |
| Float against quantized parity, scale utilization | measurement | Recorded in the sidecar from the existing `compute_quantization_parity` and `compute_scale_utilization`, no threshold |
| Corpus material sign agreement per side, side gap, correlations, mirror difference | measurement | Reported next to the gates, with no threshold |

Orientation is checked on controlled positions, not on a corpus statistic. `orientation_positions.epd` holds six quiet positions with a decisive material difference (a queen or two rooks against a bare king, a queen and rook against pawns, a full army against two rooks), each in four forms: the advantaged colour is White or Black, and it is to move or not, 24 positions in all. The expected sign of the mover's score is known by construction, and the gate requires it on every position, with a zero score counting as wrong. The file is generated by `controlled_forms` and a test checks that it is. The negative controls in the tests are a score list inverted for every position (fails all 24), one inverted for Black to move only (fails exactly the 12 Black-to-move positions while the White-to-move half stays perfect), and a network with its output layer negated. The last two run through the real quantized evaluator: a small network that really knows material passes the gate, and the same network with its output layer negated has scores identical in magnitude (so no magnitude comparison between them can tell them apart) and fails all 24. A test also ties the gate's expected signs to the Python reference's own side-to-move convention, so a White-relative reference would fail it.

The corpus statistics are measurements and not gates because material is a poor proxy for the score in tactical positions and a trained network is not exactly mirror-symmetric. Sign agreement and correlation are different metrics and are reported separately. The 0.94 to 0.98 correlations measured by hand in #327 on five networks are a reference for reading the numbers, not a calibration of a rejection limit.

## Real-data execution sequence (not run; waits for the owner to confirm the host is free)

Nothing below has been run. Every step reads or writes only the gitignored `trainer/outputs/` of the checkout that holds the data (written `$OUT` below, which is that directory) and never touches an original dataset, a checkpoint or a `.nnue` already there. Commands run from `trainer/` of a checkout of the merged `develop` with the trainer environment (`PYTHONPATH=.`), so the code is the integrated code and not a branch. All new files go under one new directory, `$OUT/screening-2026-11-27/`, which must not exist yet. The whole sequence runs as one batch once the owner confirms the host is free, with no separate approval per step. A step that fails its stop condition stops the batch and is reported with its output, and nothing later is run on a guess. No training, no match, no benchmark appears anywhere in it.

**Step 0. Preconditions and identities.**
- The owner has confirmed the host is free. Record `git rev-parse HEAD` of the checkout and `git status --short` (the code must be a clean merged `develop`).
- Build the strict engine from that commit: `mvn -pl engine-core,engine-uci -am package -DskipTests` (CI has already run the tests at that commit), and record the JAR's SHA-256. Every engine step below uses this JAR with `--engine-jar`.
- Record the SHA-256 of both original datasets so that step 4 can show they did not change: `sha256sum $OUT/datasets/stage1-lichess/manifest.json $OUT/datasets/stage1-lichess/stage1.csv $OUT/datasets/stage1-lichess-100k/manifest.json $OUT/datasets/stage1-lichess-100k/stage1.csv`. Expected: the 20k manifest `213c3d2b...` and `stage1.csv` `a9d338b2...`, and the 100k `stage1.csv` `5be437e0...`.
- `mkdir $OUT/screening-2026-11-27` (fails if it exists, which is the point).

**Step 1. Semantics probe, read-only.** For each of `stage1-lichess` and `stage1-lichess-100k`: `python -m scripts.probe_stage1_label_semantics $OUT/datasets/<dir> > $OUT/screening-2026-11-27/probe-<dir>.json`. Expected exit 0 and `"verdict": "white-perspective"` for both (the planning measurement was +0.260 and +0.201 for the 20k set, +0.236 and +0.199 for the 100k set). An `inconclusive` or `mover-relative` verdict stops the sequence: no repair.

**Step 2. Audit, read-only.** `python -m scripts.repair_stage1_perspective audit $OUT/datasets/<dir> --json $OUT/screening-2026-11-27/audit-<dir>.json` for both. Expected Black-to-move rows with a label: 9,476 (20k) and 47,313 (100k), matching the earlier audits.

**Step 3. Repair into new directories.** `--confirm-white-perspective` is authorized by the owner for the two identified legacy datasets, on the condition that all of these hold, and no further approval is needed when they do: the dataset hashes match the recorded ones (step 0), the provenance matches (the manifest hash `213c3d2b...` for the 20k set and the 100k manifest in `2026-11-27-stage1-repair-provenance.md`), step 1 gave `white-perspective` for it, the directory carries no `label_perspective` marker and no previous repair (the tool refuses a marked one), the output is a new directory (the tool refuses an existing target), the affected-row count in step 2 is 9,476 (20k) and 47,313 (100k), and step 4 then passes. If any condition does not hold, the repair for that dataset does not run and the batch stops with the reason. With the conditions met:
- `python -m scripts.repair_stage1_perspective repair $OUT/datasets/stage1-lichess $OUT/datasets/stage1-lichess-mover-relative-v2 stage1-lichess-evals-2026-07-15-mover-relative-v2 --confirm-white-perspective`
- `python -m scripts.repair_stage1_perspective repair $OUT/datasets/stage1-lichess-100k $OUT/datasets/stage1-lichess-100k-mover-relative-v2 stage1-lichess-evals-2026-07-20-100k-mover-relative-v2 --confirm-white-perspective`
A second run of either command is refused (an existing target and an already marked directory), and that refusal is recorded as evidence. The new directories are never deleted by the batch. If step 4 fails for one, the batch stops and the failed directory is kept for inspection, not used.

**Step 4. Verify the repair, and re-hash the originals.** For each pair: `python -m scripts.verify_stage1_repair $OUT/datasets/<orig> $OUT/datasets/<repaired> > $OUT/screening-2026-11-27/verify-<dir>.json`. Expected exit 0 and `all_checks_pass: true`. Then repeat the `sha256sum` of step 0 and require byte-identical hashes, and confirm production accepts the repaired directories by the split run in step 6.

**Step 5. Stage 2 identity checks.** Which Stage 2 directory each run used, and whether the `-v1` copies equal the legacy ones:
- `find $OUT -name provenance.json -path '*P5*'` and read the Stage 1 and Stage 2 hashes it records; `sha256sum $OUT/datasets/stage2-quiet-sf*/shard-0.bin` for the four directories, and compare with the recorded hashes. Expected for P5: Stage 1 as in step 0, Stage 2 `stage2-quiet-sf-wdl` (shard `4955f2e5...`).
- Record-for-record comparison of each legacy directory with its `-v1` copy. The legacy shards have no header and cannot be read by the production provider, so `compare_stage2_records` migrates each into a temporary directory with the existing `migrate_legacy*_to_v1` functions and compares the records, leaving every source untouched:
  `python -m scripts.compare_stage2_records $OUT/datasets/stage2-quiet-sf legacy119 $OUT/datasets/stage2-quiet-sf-v1 v1 > $OUT/screening-2026-11-27/stage2-compare-sf.json`

  The outcome is exactly one of `identical`, `ordering-mismatch`, `content-mismatch` or `reader-failure` (exit 0 only for `identical`), tested on synthetic legacy and v1 fixtures. The `-v1` shard of the non-WDL directory has a recorded zero-mismatch migration, and the `-wdl-v1` copy has none, so the second comparison is the one that establishes it. Anything but `identical` for the WDL pair means the held-out reproduction in step 6 cannot be expected and is reported as such, and the batch continues (Step 6 reads the `-v1` copy because the production reader cannot read the legacy shard).

**Step 6. Repair invariance and the historical held-out reproduction (reported separately).** For the 20k pair with the `-v1` copy of the Stage 2 directory step 5 identified as the P5 one (the production reader cannot read the legacy shard):
`python -m scripts.verify_stage1_repair $OUT/datasets/stage1-lichess $OUT/datasets/stage1-lichess-mover-relative-v2 --stage2-dir $OUT/datasets/stage2-quiet-sf-wdl-v1 --seed 42 --expect-held-out-sha256 0a183465b4fa890be1a78e329f30b88d688aa93f76a215171be81fcf88a87134 > $OUT/screening-2026-11-27/split-20k.json`
- Repair invariance (`split.split_membership_invariant`) must be true: the repair moved no position between training and held-out.
- Reproduction of the historical hash (`split.historical_held_out_reproduced`) may legitimately be false for reasons unrelated to the repair. It is reported with both hashes and the cause step 5 found, and never changes the repair. If it is false, the original-label figure is confirmed only with the old commit `3579a3c` in a throwaway worktree.
- Run it a second time with `--drop-duplicates` and without `--expect-held-out-sha256` to record the split a new training run would get (`train_candidate_net.main` uses `drop_duplicates=True`).

**Step 7. Checkpoint inventory and the shortlist.** Write `$OUT/screening-2026-11-27/labels.json` mapping each label in `shortlist_groups.json` to its checkpoint path relative to `$OUT`, from the checkpoints named in the 2026-11-24 audit (listed here from the directory, not yet hashed): `E-3`: `nets/checkpoint.pt`; `P1-G04`: `phase1/P1-G04/final.pt`; `P3A-001`: `phase3/P3A-001/final.pt`; `P4IV-001`: `phase4/P4IV/P4IV-001-wdl-blend/final.pt`; `P5-control-selected` and `P5-treatment-selected`: `phase5/P5-AUXHEAD-RMS/{control,treatment}/checkpoints/step-003999.pt`; `P5-control-final` and `P5-treatment-final`: `phase5/P5-AUXHEAD-RMS/{control,treatment}/final.pt`; `E15-control-final` and `E15-treatment-final`: `phase-e15/{control,treatment}/final.pt`; `E16-control-s4N-final` and `E16-treatment-s4N-final` for N in 2, 3, 4: `phase-e16/checkpoints/{control,treatment}/e16-{control,treatment}-seed4N-final.pt`; `M1-s4N-final` for N in 2, 3, 4: `phase-m1/cp-only-noise-floor/seed4N/final.pt`. `M1-s42-final` stays in the file even though it belongs to no group, because it is the second label of the `P1-G04` network. Then: `python -m scripts.checkpoint_inventory --input $OUT/screening-2026-11-27/labels.json --root $OUT --output $OUT/screening-2026-11-27/inventory.json --shortlist`. Checkpoints load with `weights_only=True`, and the tool says so if one needs `--trust-checkpoint`, which is only ever given for a file this project produced and only after the owner agrees. Read the result: the deployed networks with their labels (confirm `P1-G04` and `M1-s42-final` are one network and compare the hash prefixes with the audit note), `excluded` with its reasons, `candidate_count` (at most 10) and `network_count` (at most 11, the anchor included), and any shared arm. **Step 8. Rescore the shortlisted networks on corrected held-out labels.** Inference only, one prediction vector per network, scored with `evaluate_held_out` against the original and the corrected labels of exactly the same ordered held-out records, using the historical split path that the frozen checkpoints were trained against (no `--drop-duplicates`):
`python -m scripts.rescore_held_out --inventory $OUT/screening-2026-11-27/inventory.json --labels $OUT/screening-2026-11-27/labels.json --root $OUT --original-stage1 $OUT/datasets/stage1-lichess --corrected-stage1 $OUT/datasets/stage1-lichess-mover-relative-v2 --stage2-dir $OUT/datasets/stage2-quiet-sf-wdl-v1 --seed 42 --output $OUT/screening-2026-11-27/rescore.json`

Stop condition: the tool refuses if the two datasets do not have the same ordered FEN sequence or the predictions differ between the label sets. Expected: only the `public` Black-to-move group has differing labels. A network whose Black-to-move correlation changes after the correction is reported as that, with no interpretation beyond the numbers.

**Step 9. Export each shortlisted network and run Stage 0.** For each deployed network (one checkpoint per identity, the first label in `networks[].labels`), into a new directory `$OUT/screening-2026-11-27/nets`:

Record the JAR hash and the platform with the results. The exports go on to Stage 1 only if the owner approves a match run, which this sequence does not contain.

The repaired dataset loads through production `combine_and_split`. The original arm cannot, because production correctly refuses legacy white-perspective data, so it needs the isolated historical-label control specified in the plan (a separate module that requires an acknowledgement and a pinned manifest hash, refuses a marked dataset, shares the split code with production without touching its guard, and labels everything it produces as a legacy control).
