# Failing closed when an NNUE experiment cannot use its network

2026-11-27. Issue #330, roadmap step 2 of the strength assessment (#327). An engine told `EvalType=NNUE` that cannot use the network prints an `info string` and plays Classical. Under Cute Chess that line is not kept and `readyok` has already been sent, so an NNUE experiment can silently be a Classical run. The E-5 launch command is not in the artifacts, so there is no way to show now whether its NNUE side used the net.

## Two guarantees, kept apart

The engine can only act on what it is told, so the fix has two parts.

**Engine.** A new `StrictNnue` option (check, default false). With it on, `EvalType=NNUE` plus an empty, missing, unreadable or loader-rejected `EvalFile`, or an `EvalType` value that is neither Classical nor NNUE, prints one `info string NNUE strict mode: <reason>` line and exits with status 2 before `readyok`. The check runs at `isready` and again at `go`, `eval`, `nnue` and `bench`, so options changed after `isready` cannot reach a search. `EvalType=Classical`, and every path with strict off, behave exactly as before, and the three existing fallback tests pass unedited. An option sent under a misspelled name is ignored under the UCI rules, so the engine never learns about it. A test pins that limit (`misspelledOptionNameIsOutOfScopeForTheEngine`) so nobody later assumes strict mode covers it.

**Launcher.** `tools/nnue_preflight.py` launches what the match will launch: the same Java executable, JVM arguments, JAR and options in the same order, taken from the Cute Chess argument array. It rejects an option given twice (whether or not the values agree), an option the engine does not advertise (which is how a misspelled `EvalType` is caught), an option that differs only in case, an `EvalType` value other than exactly `Classical` or `NNUE`, NNUE without an absolute `EvalFile` or without `StrictNnue=true`, and `EvalFile` on a Classical engine. An NNUE side also needs a pinned uuid and file SHA-256. The tool computes the hash, checks the uuid the engine reports, and the launcher recomputes the hash immediately before starting Cute Chess. A sibling manifest, when present, must agree. When none exists the record says `unverified-manifest-absent`: the bytes matched the pin, and no provenance is claimed.

`tools/fixed_count_match.py` runs it for every side of an NNUE run (`--new-nnue-uuid`, `--new-nnue-sha256`, and the `--old-` pair) before anything starts, records the result in the provenance JSON, and re-checks the file right before launch. `tools/nnue-gauntlet.ps1` now takes `-NnueUuid` and `-NnueSha256`, adds `option.StrictNnue=true`, and runs the same pre-flight. A Classical-only run builds the same arguments and provenance as before. The demonstration launchers are unchanged.

## What it does not do

The SPRT scripts hard-code `EvalType=Classical` and are not touched. Strict verification is a prerequisite for any future NNUE SPRT, and wiring it into them is part of that work. The pre-flight is a one-second handshake, and the match engines are separate processes, so it proves the configuration, not each later launch. Strict mode is what makes a later launch fail loudly if something differs.

## Verification

Child-process tests for each engine-detectable failure (exit status 2 within 5 seconds, one explanatory line, no `readyok`, no `bestmove`), the valid-network and Classical paths, order independence, the backstop at `go`, and the unchanged non-strict behavior. Removing the `System.exit(2)` makes six of the eleven tests fail. The pre-flight has 32 tests against a fake engine (each rejection, the exact launched command line, the pins, the manifest cases, a hung engine, an engine that exits before `readyok`), and the launcher guard has 14 (each refusal happens before Cute Chess starts, a network swapped after the pre-flight is caught by the re-check, the provenance carries the record).

Real engine, native Windows, `--prepare-only` (no match): a strict JAR with the `dfffd3da` network and correct pins passes and writes the manifest and provenance. Without `StrictNnue` (status 3), with a wrong hash pin (status 6), with `Threads` given by both the launcher and a user option (status 3), and with the JAR from before this change as the NNUE side (status 3) the launcher refuses before Cute Chess is started. The PowerShell gauntlet parses, and with a wrong pin exits before any match. The native run also found a real bug: `fixed_count_match.py` loads helper modules by path without registering them in `sys.modules`, and on Python 3.12 a dataclass defined under `from __future__ import annotations` then fails at import. It did not show on the Python 3.15 used for the unit tests, so the pre-flight no longer uses that import and a test pins that.
