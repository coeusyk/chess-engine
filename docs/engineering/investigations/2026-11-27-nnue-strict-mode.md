# Failing closed when an NNUE experiment cannot use its network

2026-11-27. Issue #330, roadmap step 2 of the strength assessment (#327). An engine told `EvalType=NNUE` that cannot use the network prints an `info string` and plays Classical. Under Cute Chess that line is not kept and `readyok` has already been sent, so an NNUE experiment can silently be a Classical run. The E-5 launch command is not in the artifacts, so there is no way to show now whether its NNUE side used the net.

## Two guarantees, kept apart

The engine can only act on what it is told, so the fix has two parts.

**Engine.** A new `StrictNnue` option (check, default false). With it on, `EvalType=NNUE` plus an empty, missing, unreadable or loader-rejected `EvalFile`, or an `EvalType` value that is neither Classical nor NNUE, prints one `info string NNUE strict mode: <reason>` line and exits with status 2 before `readyok`. The check runs at `isready` and again at `go`, `eval`, `nnue` and the UCI `bench` command, and the search worker repeats it where it resolves the network, so an `EvalFile` or `EvalType` option that arrives after the check at `go` ends the process instead of switching to Classical (UCI forbids `setoption` during a search, but nothing in the engine enforces that, and the option fields are now volatile because the worker reads them). A network that loads is cached and its `NNUE network loaded: <uuid>` line is printed at `isready`, not at the first `go` as in the non-strict path. The command-line `--bench` entry point does not go through any of this and is out of scope: it has no strict flag, and the launchers use UCI. `EvalType=Classical`, and every path with strict off, behave exactly as before, and the three existing fallback tests pass unedited. An option sent under a misspelled name is ignored under the UCI rules, so the engine never learns about it. The engine lower-cases option names, compares the `EvalType` value ignoring case and lets the last duplicate win. A test pins that limit (`misspelledOptionNameIsOutOfScopeForTheEngine`) so nobody later assumes strict mode covers it.

**Launcher.** `tools/nnue_preflight.py` launches what the match will launch: the same Java executable, JVM arguments, JAR and options in the same order, taken from the Cute Chess argument array. It rejects an option given twice (whether or not the values agree), an option the engine does not advertise (which is how a misspelled `EvalType` is caught), an option that differs only in case, an `EvalType` value other than exactly `Classical` or `NNUE`, NNUE without an absolute `EvalFile` or without `StrictNnue=true`, and `EvalFile` on a Classical engine. An NNUE side also needs a pinned uuid and file SHA-256. The tool computes the hash, checks the uuid the engine reports, and the launcher recomputes the hash immediately before starting Cute Chess. A sibling manifest, when present, must agree. When none exists the record says `unverified-manifest-absent`: the bytes matched the pin, and no provenance is claimed.

`tools/fixed_count_match.py` sends a side through it whenever any of its options is named `EvalType`, `EvalFile` or `StrictNnue` in any case, not only when the value is exactly `NNUE`: an exact-case gate would let `evaltype=NNUE`, `EvalType=nnue` or a repeated `EvalType` start an unverified NNUE match, because the engine accepts all of them. It also refuses `-each option.*` and `-each initstr=`, which reach every engine outside any `-engine` block. It runs the pre-flight for every side of an NNUE run (`--new-nnue-uuid`, `--new-nnue-sha256`, and the `--old-` pair) before anything starts, records the result in the provenance JSON, re-checks the file right before launch and again when the run ends (`nnue_network_unchanged_after_run` in the provenance), and its prepared-record comparison includes each side's network hash and pinned uuid. `tools/nnue-gauntlet.ps1` now takes `-NnueUuid` and `-NnueSha256`, adds `option.StrictNnue=true`, and runs the same pre-flight. A Classical-only run builds the same arguments and provenance as before. The demonstration launchers are unchanged.

## What it does not do

The SPRT scripts hard-code `EvalType=Classical` and are not touched. Strict verification is a prerequisite for any future NNUE SPRT, and wiring it into them is part of that work. The pre-flight is a one-second handshake, and Cute Chess starts the match engines itself, and again after a crash under `-recover`, so the handshake proves the configuration at that moment and not each later launch. Strict mode makes a later launch fail loudly if the network cannot be loaded. It does not notice a different but valid network swapped in afterwards, because the engine has no expected-uuid check by design (the pin is checked from outside), which is why the launcher re-checks the file hash at launch and after the run.

## Verification

Child-process tests for each engine-detectable failure (exit status 2 within 5 seconds, one explanatory line, no `readyok`, no `bestmove`), the same at `eval`, `nnue` and `bench` without an `isready`, any case of `nnue` as the `EvalType` value, the valid-network and Classical paths, order independence, the backstop at `go`, and the unchanged non-strict behavior (14 tests). Removing the `System.exit(2)` makes six of the first eleven fail. The race between a late `setoption` and the worker is closed in code but has no deterministic test, because the timing is not controllable from outside. The pre-flight has 39 tests against a fake engine (each rejection, the exact launched command line, the pins in any case, the manifest cases including a corrupt or non-object one, a missing network file, a hung engine that is shown to be dead afterwards, an engine that exits before `readyok`, host-specific absolute paths, `-each` options), and the launcher guard has 22 (each refusal happens before Cute Chess starts, including lowercase and duplicated `EvalType`, a network swapped after the pre-flight or during the run, the prepared-record comparison, the provenance record).

Real engine, native Windows, `--prepare-only` (no match): a strict JAR with the `dfffd3da` network and correct pins passes and writes the manifest and provenance. Without `StrictNnue` (status 3), with a wrong hash pin (status 6), with `Threads` given by both the launcher and a user option (status 3), and with the JAR from before this change as the NNUE side (status 3) the launcher refuses before Cute Chess is started. The PowerShell gauntlet parses, and with a wrong pin exits before any match. The native run also found a real bug: `fixed_count_match.py` loads helper modules by path without registering them in `sys.modules`, and on Python 3.12 a dataclass defined under `from __future__ import annotations` then fails at import. It did not show on the Python 3.15 used for the unit tests, so the pre-flight no longer uses that import and a test pins that.
