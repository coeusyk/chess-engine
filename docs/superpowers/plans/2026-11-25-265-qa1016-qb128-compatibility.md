# QA 1016 / QB 128 compatibility evidence Implementation Plan

> Executed under the owner's engineering-plan policy (`~/.agents/ENGINEERING_WORKFLOW.md`, `engineering-plan` skill). The execution record at the end of this file is the tracker. Steps use checkbox syntax.

**Goal:** Add committed, cross-language evidence that a network exported at QA 1016 / QB 128 loads, evaluates and updates incrementally correctly, with no change to production quantization, defaults or networks. "Correct" means Java equals the Python reference exactly within each scale. Nothing here claims that quantized scores are equal across scales: a different grid gives different rounding, and that difference is the quantization error #312 measured.

**Evidence classes.** This plan produces synthetic compatibility evidence (a seeded synthetic network checked into the repo, and fuzz over synthetic weights). The one-checkpoint probe described in the investigation section is a real-checkpoint measurement. The two are kept apart in every record this plan creates, and neither stands in for the other.

**Architecture:** Extend the existing #265 fixture machinery (one new frozen `.nnue` fixture, one golden CSV, one entry in each of the Java and Python fixture lists) and parametrize the existing incremental-vs-rebuild fuzz test over the scale. Test and resource files only. The investigation findings go into one case study and one Phase 22 entry.

**Tech Stack:** Java 21 and JUnit 5 (engine-core), Python and pytest (trainer), the existing exporter and `NnueFixtureGoldenGenerator`.

**Spec:** Issue #265, `docs/architecture/research/nnue/2026-11-24-weight-scale-alternatives.md` (the open points), and the findings below.

**Status:** Investigation done, plan drafted, not approved, nothing implemented. Branch `research/265-qa1016-compat` (local, from develop at `be7cfff`), uncommitted.

## What the investigation established (2026-11-25, develop `be7cfff`)

Method: read the trainer quantizer, exporter and reference inference, the Java loader, evaluator and vector ops, and the #313 dot kernel. Then, as a throwaway probe that is not part of the repo, rescaled the P5 control final checkpoint (`rescale(base, 8, 2)`, which is QA 127 to 1016 and QB 64 to 128 with the float function unchanged), exported both scales with the production `quantize()` and exporter byte writer, scored the 393-position bench corpus with the Python bit-exact reference, and ran the real Java loader and evaluator over the same files, on the #313 branch so the vector dot kernel was included. No match, training or benchmark was run.

| Layer | Supported today? | Evidence |
|---|---|---|
| Trainer `quantize()` | Yes, QA-agnostic | Round-to-nearest plus int16 clip and a worst-case accumulator check. `validate_qa` allows 1 to 32767, `validate_qb` any integer of 1 or more. Rescaled P5 final: FT max abs weight 156 at QA 1016 (19 at QA 127), output max 92, 0 loader-bound violations. |
| Exporter and header | Yes | `qa`, `qb`, `outputScale` are int32 header fields, `qa` checked against int16. The file is self-describing. |
| Trainer clip bounds | Fine for this net, a training-time question for others | `derive_weight_clip_bounds(1016)` gives bias clip 1016 and weight clip 992, against a measured max of 156. |
| Java loader | Yes | `qa` 1 to 32767 (header range test already covers 1, 64, 127, 128, 255, 256, 512, 32767), `qb` positive, worst-case 32-feature accumulator check. Both probe files loaded. |
| Accumulator and incremental updates | Yes, QA-independent | Plain int16 add and subtract. Probe: 2,400 random-game checks, 0 divergences from a scalar rebuild at each scale; accumulator range [-798, 366] at QA 1016. |
| Scalar inference | Yes | `evaluate()` uses `long` products. Probe: Java equals the Python reference on 393 of 393 positions at both scales. |
| Vector accumulator ops | Yes, QA-independent | Elementwise `short` add and subtract, no QA in the arithmetic. |
| Vector output dot (#313, unmerged) | Yes, behind a guard | Int-lane sums are used only when `qa * sum(abs(w))` fits an int (`dotFitsInt`), else the scalar loop. On the P5 net the ratio is 0.0007 at QA 127 and 0.0106 at QA 1016. Probe: kernel equals scalar on 393 of 393 positions. #313's own equivalence test already covers the guard boundary and QA 1016. |
| Hard-coded 127 in production | None found | The only QA constants in main code are the loader's `MAX_QA = 32767`. |

**What requires modification:** nothing in production code for the measured network.

**What is not covered by any committed test:** no committed test evaluates a network at QA other than 127 end to end. The two golden fixtures and `TestNetworks.synthetic` are all QA 127 / QB 64, so the Python-versus-Java zero-difference check and the incremental fuzz never run at another scale. The probe above is that evidence today, and it is not reproducible from the repo.

**Not established:** other checkpoints beyond P5 control final (the #312 headroom figures cover the other 12 statically), play strength, and training at QA 1016 (FT initialization, learning rate and clipping all depend on QA and are a retraining question, deliberately out of scope).

## Amendments (owner, 2026-11-25)

1. Exact Java/Python agreement is required within each scale. No test compares scores across scales.
2. Clipping coverage is asserted, not assumed: on the 393-position corpus the fixture must produce accumulator values above `qa` and below 0, as counts that the tests check are greater than zero (Task 1 selection criteria, Task 2 and Task 3 assertions).
3. The output-overflow fixture must genuinely exceed the int32 bound, `qa * sum(abs(output weights)) > Integer.MAX_VALUE`, asserted in the test from the weights themselves. On develop only the scalar path exists, so that test is scalar coverage and is named as such. The guard-rejection assertion (`dotFitsInt` returns false) and the vector fallback only exist on #313, so they are Task 5, blocked on #313 merging, and are not claimed until then.
4. The real-checkpoint probe is preserved: procedure, checkpoint identity, hashes, commands and the probe scripts go into the case study folder (Task 4), separated from the synthetic evidence.
5. The Superpowers execution-skill header is removed. Execution follows the engineering-plan policy.

## Review Focus

1. A network whose output weights exceed the int32 bound must evaluate correctly on the scalar path (Task 3, scalar coverage now), and the guard must reject it and the vector path fall back (Task 5, after #313).
2. A header with `qa` at the int16 boundary and an accumulator at the loader bound edge must still load and wrap-check correctly. Existing loader test covers load, Task 3 adds an evaluate at the edge.
3. Negative scores at QB 128 must truncate toward zero exactly as in Python. Task 1 requires negative-score coverage in the fixture and Task 2 asserts it.
4. Clamping at both ends of `[0, qa]` with qa 1016 across many units. Task 1 requires it and Task 2 asserts it.
5. The incremental accumulator at wider weights (about 8x) across all move types. Task 3 runs the existing fuzz at the new scale.
