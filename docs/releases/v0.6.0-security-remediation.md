## Credential and artifact boundaries

| Job | Repository permission | Source access | Work |
| --- | --- | --- | --- |
| `build` | `contents: read` | Exact selected tag; checkout credentials are not persisted | Source/tag/master ancestry, five Maven versions, Maven verification, regression groups, executable UCI JAR smoke, bundle generation |
| `publish` | `contents: write` | No checkout | Validate downloaded data, create/resume draft, upload and verify three release assets |

The stable tag determines the version. With the five current POMs at 0.6.0,
only `v0.6.0` passes version validation. Both checkout HEAD and the peeled local
tag must match the workflow event SHA; that commit must be an ancestor of master.
The executable is exactly `engine-uci/target/engine-uci-0.6.0.jar`.

The build uploads one artifact named `vex-release-<run ID>-<run attempt>` containing:

- `engine-uci-0.6.0.jar`
- `engine-uci-0.6.0.jar.sha256`
- `release-manifest-0.6.0.json`
- `release-notes.md`

Publication downloads the immutable artifact ID returned by the successful build
in the same workflow run. It rejects a missing artifact ID, unexpected files,
directories, symlinks, empty files, missing build digests, or mismatched hashes.
All four file hashes travel independently as build-job outputs. The checksum
must name the expected JAR and digest exactly. The manifest must match the event's
stable tag and source SHA, version, JAR name, minimum Java version, and JAR hash.
Release notes must start with the matching changelog section. Downloaded content
is never executed. The publication logic is inline workflow code, outside the
artifact directory, and it runs no Maven, Java tests, or project scripts.

The final GitHub release has exactly three assets: the JAR, its checksum, and the
manifest. Notes become the release body. Every uploaded asset must be complete
and have the expected size. If GitHub reports a SHA-256 asset digest, publication
compares it to the build digest. Otherwise it downloads that asset through the
GitHub API and hashes its bytes. A filename match alone is insufficient.

## Retry and recovery

Only a successful, paginated release-list response establishes that no release
exists. Authentication, network, or API errors abort the job. A matching published
release is rejected. An existing draft may have a subset of the three expected
assets; a retry fills or replaces them. If its manifest exists, it must identify
the same source/tag before any edits. Unexpected or duplicate assets require
manual review and are not automatically deleted. A full rebuild may produce
different JAR bytes from the same source, so a draft retry replaces all expected
assets and verifies the new digests.

Publication rechecks the remote tag (including annotated-tag peeling), the draft
state, and the draft's tag before mutations. It checks the remote tag and draft
state again during/following upload. Failure leaves an unpublished draft for
inspection and retry. A publication-job-only retry reuses the original artifact;
artifacts expire after seven days, after which a full rerun is required.

Do not publish manually while a workflow run for that tag is active. GitHub's
release APIs do not offer an atomic draft-only condition across every upload,
so an operator publishing between a state check and upload remains a race.
Workflow concurrency serializes workflow runs for the same tag, not UI actions.
Tag rules below prevent tag movement; they do not lock release publication.
Actions retain the repository's existing major-version reference style.

## Recommended governance settings (not applied)

The current active ruleset is `protect-master` (ID 14287003), targeting
`~DEFAULT_BRANCH`. It requires zero approvals and has no required status checks.
The admin repository role (actor ID 5) can always bypass it. No tag ruleset was
present during inspection. These are settings recommendations, not API changes.

Keep `protect-master` active, target `refs/heads/master` explicitly, retain
creation/deletion/force-push restrictions, and add this rule:

```json
{
  "type": "required_status_checks",
  "parameters": {
    "strict_required_status_checks_policy": true,
    "required_status_checks": [
      {"context": "build-and-test", "integration_id": 15368}
    ]
  }
}
```

Strict enforcement requires the PR source to include current master and receive
fresh CI. Develop currently lacks the master-only integration commit; adopting
strict mode can therefore require a separately authorized forward merge from
master into develop and another CI run. Preserve existing evidence history.
The rule targets master branch updates, so it does not block the manual release
workflow running against an existing tag. If a merge queue is later enabled,
add `merge_group` to CI before requiring this context for queued merges.

Desired pull-request policy: one independent approval, dismiss stale approvals
on new commits, require approval of the last push, require resolved review
threads, and allow the merge-commit method. Remove the broad admin bypass
(`bypass_actors: []`) if these requirements must be mandatory. An independent
reviewer must be available; an author cannot approve their own PR. CODEOWNERS is
currently absent, so enabling code-owner review alone does not establish a
reviewer. Assign owners in a separate reviewed change if that policy is wanted.

Use two active tag rulesets with no excluded refs:

```json
{
  "name": "release-tag-creation",
  "target": "tag",
  "enforcement": "active",
  "conditions": {"ref_name": {"include": ["refs/tags/v*"], "exclude": []}},
  "bypass_actors": [
    {"actor_type": "User", "actor_id": 69001824, "bypass_mode": "always"}
  ],
  "rules": [{"type": "creation"}]
}
```

User ID 69001824 is `coeusyk`, verified through GitHub on 2026-10-12. Confirm that
this account remains the authorized release maintainer before applying the rule.
Do not add the Actions app or broad repository roles to the creation bypass list.

```json
{
  "name": "immutable-release-tags",
  "target": "tag",
  "enforcement": "active",
  "conditions": {"ref_name": {"include": ["refs/tags/v*"], "exclude": []}},
  "bypass_actors": [],
  "rules": [
    {"type": "update", "parameters": {"update_allows_fetch_and_merge": false}},
    {"type": "deletion"}
  ]
}
```

The creation bypass applies only to its ruleset. With no bypass in the second
ruleset, that maintainer cannot update or delete an existing matching tag.
Admins can still edit rulesets; audit and review any emergency settings change.
Audit existing `v*` targets before activation. Prefer a new version for a bad
published release rather than moving an existing tag. Recovering a mistyped tag
would require an explicit, audited ruleset change, then restoration of protection.

GitHub documents these fields and bypass semantics in its
[repository rules API](https://docs.github.com/en/rest/repos/rules) and
[available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
No live tag push or ruleset mutation was used to test enforcement.
