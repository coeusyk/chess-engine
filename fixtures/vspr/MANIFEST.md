# VSPR canonical fixtures (#211)

Byte-exact golden fixtures for the VSPR wire format defined by
[`DR-220-vspr-wire-format.md`](../../docs/architecture/research/DR-220-vspr-wire-format.md)
(section 10). These bytes are the interoperability oracle: both the Java codec
(`engine-core`) and the Python decoder (`trainer`) are tested against these exact files
independently — neither language's implementation is used to generate them, and no test
regenerates an expected hash from the codec under test.

**Provenance:** the six `valid_*` files were extracted directly from DR-220's own committed
hex blocks (section 10) and independently re-verified (length, SHA-256 against the doc's own
stated hash, CRC-32 of the frame body) via a one-off, non-committed materialization script
before being written to disk — not generated by, or cross-checked against, the Java or Python
codec. The three `invalid_*` files are DR-220's own documented byte-level mutations of
`valid_01_ordinary_cp_sample.vspr` (truncation, a single-byte `formatVersion` flip, a
single-byte `gameOutcome` flip); their hashes are newly established by this commit, since
DR-220 documents the mutation precisely but does not pre-state their resulting hashes.

**Refinement to `invalid_09`:** DR-220 section 10 documents this fixture as a single-byte
`gameOutcome` flip and doesn't say whether the frame's trailing CRC-32 should be repaired
afterward. A bare byte flip with the old CRC left in place is *also* a CRC mismatch, which a
correct decoder reports before ever reaching enum validation — masking the specific case this
fixture's own stated purpose is to exercise ("`0xFF` is not a defined `GameOutcome` value"). This
matches DR-220's own established convention for every other constructed fixture ("`frameLength`/
`crc32` recomputed" — Fixtures 6 and 7), so the CRC here is likewise recomputed after the flip,
isolating the intended `INVALID_ENUM` path. Caught by the Java contract suite expecting
`INVALID_ENUM` and observing `CRC_MISMATCH` instead — exactly the kind of gap this
materialize-before-codec discipline exists to surface.

## Regenerating / verifying independently

Every value above can be reproduced with standard tools, with no VSPR-aware code at all:

```bash
sha256sum fixtures/vspr/*.vspr
```

CRC-32 verification (the frame body's own integrity check, distinct from the file's SHA-256)
requires locating the frame body within each `valid_*` file: the fixed V1 header is exactly 120
bytes, followed by a 4-byte big-endian `frameLength`, the frame body itself, and a trailing
4-byte big-endian CRC-32 (IEEE 802.3) of that body — see DR-220 section 4 for the exact layout
and section 10 for per-fixture field values.
